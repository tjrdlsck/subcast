# Subcast Google Drive 백업 및 충돌 분기 고도화 기획서

- 상태: 제안 초안, 구현 승인 아님
- 작성일: 2026-10-11
- 목적: Supabase 같은 별도 사용자 데이터베이스 없이 사용자 계정의 Google Drive에 프로젝트 백업을 보관하고, 다른 기기에서 오래된 데이터를 저장해도 작업물이 덮어써지지 않도록 한다.

## 1. 제안 요약

Subcast는 현재처럼 프로젝트를 PC에 저장하고, 사용자가 명시적으로 백업·복원할 때 Google Drive를 이용한다. 프로젝트 백업은 썸네일을 제외한 압축 스냅샷으로 저장하고, 동영상과 글꼴 등 프로젝트가 참조하는 파일은 Drive에 별도 자산으로 보관한다. 각 스냅샷은 수정하지 않는 새 파일로 만들고 이전 스냅샷 ID를 기록한다.

다른 PC가 같은 스냅샷을 바탕으로 작업했더라도 한쪽 파일을 덮어쓰지 않는다. 두 작업이 같은 부모 스냅샷에서 갈라졌다면 앱에서 별도 분기로 표시하고, 사용자가 이어서 쓸 작업물을 고르게 한다. 자동 병합이나 실시간 공동 편집은 초기 범위에서 제외한다.

**결정 제안**

- 사용자 계정과 저장 공간: Google 계정 및 사용자 Google Drive
- 별도 Supabase 계정·데이터베이스: 사용하지 않음
- 로컬 앱 동작: 인터넷 연결 없이 계속 사용 가능
- 클라우드 동작: 명시적 백업, 백업 목록 조회, 복원
- 충돌 정책: 덮어쓰기 금지, 충돌 스냅샷을 별도 프로젝트 분기로 보존
- 동시 편집: 지원하지 않음. 편집 시작과 백업 화면에서 단일 편집자 안내
- 자동 병합·실시간 동기화: 초기 범위에서 제외

## 2. 현재 프로그램 기준선

확인한 현재 구조는 다음과 같다.

- 프로젝트 데이터는 `backend/storage.py`에서 `data/projects/<project_id>.json` 파일로 로드·저장한다. 저장은 프로세스 내 `asyncio.Lock`, 임시 파일 작성, `os.replace`를 사용한다. 이 잠금은 한 PC의 한 백엔드 프로세스에만 유효하며 다른 PC의 저장을 조정하지 않는다.
- 프로젝트 내보내기와 가져오기는 `backend/routers/projects.py`에 있다. 현재 내보내기는 프로젝트 JSON을 반환하고, 가져오기는 새 로컬 프로젝트 ID를 만들어 등록한다.
- `ProjectData`는 프로젝트 설정, 슬라이드, 템플릿, 사용자 글꼴 메타데이터를 포함한다. 각 슬라이드는 요소와 선택적 썸네일을 포함한다.
- 썸네일은 1920×1080 캔버스 JPEG 데이터 URL로 생성되어 프로젝트 데이터에 들어갈 수 있다. 클라우드 백업에서는 제거하고 로컬에서 재생성하는 편이 저장량을 크게 줄인다.
- 배경 동영상은 프로젝트 JSON 외부의 로컬 파일이다. 프로젝트 설정은 `/static/backgrounds/<파일명>` 형태의 경로를 참조한다. 사용자 글꼴도 글꼴 바이너리와 메타데이터가 별도 경로에 있을 수 있다.
- 웹소켓 편집기 잠금은 서버 메모리의 `locked_slides`에 보관된다. 따라서 현재 잠금은 같은 로컬 백엔드에 연결된 클라이언트 사이에서만 동작하며 PC 간 잠금으로 간주할 수 없다.
- 찬양곡 데이터, 성경 데이터, 전역 템플릿, 태그, 모니터 설정 및 앱 설정은 프로젝트 JSON과 저장 위치가 다를 수 있다. 이 기획서의 초기 백업 범위는 프로젝트와 해당 프로젝트가 참조하는 자산으로 제한한다.

## 3. 목표와 비목표

### 목표

1. Google Drive에 프로젝트의 복구 가능한 백업을 만들고 다른 PC에서 복원한다.
2. 썸네일 같은 파생 데이터를 제외하여 클라우드 전송량과 보관량을 줄인다.
3. 동시 작업으로 서로 다른 수정본이 생겨도 어느 쪽도 조용히 사라지지 않게 한다.
4. 새 설치·기존 데이터 유지·오프라인 편집 흐름을 해치지 않는다.
5. Google Drive 권한을 백업 파일과 앱이 생성한 자산으로 최소화한다.

### 초기 범위에서 제외

- 여러 PC의 실시간 공동 편집과 편집 내용의 실시간 브로드캐스트
- 자동 병합 및 같은 슬라이드 내 변경의 세밀한 병합
- 서비스 운영자가 데이터를 보관하는 중앙 저장소
- 찬양곡 DB, 성경 DB, 전역 태그, 모든 모니터·트레이 설정까지 포함한 PC 전체 백업
- 앱을 제거하거나 Drive 연결을 해제했을 때 Drive 백업까지 자동 삭제

## 4. 사용자 시나리오

### 4.1 최초 Drive 연결

1. 사용자가 앱의 클라우드 백업 메뉴에서 Google Drive 연결을 선택한다.
2. 기본 브라우저에서 Google 계정 인증과 Drive 권한 동의를 진행한다.
3. 앱은 사용자에게 백업 파일을 저장할 `Subcast` 폴더를 만든다고 설명한다.
4. 연결이 끝나면 앱은 계정 표시명 일부와 연결 상태만 로컬에 표시한다. 액세스 토큰이나 리프레시 토큰은 화면·로그·프로젝트 JSON에 노출하지 않는다.

### 4.2 프로젝트 백업

1. 사용자가 프로젝트에서 `클라우드 백업`을 누른다.
2. 앱은 로컬 저장 대기열을 비우고 현재 프로젝트를 다시 읽어 스냅샷을 만든다.
3. 썸네일 데이터와 재생 가능한 파생 캐시는 제외하고, 프로젝트 스키마 버전·파일 해시·자산 목록을 포함해 압축한다.
4. 먼저 아직 Drive에 없는 자산을 업로드하고, 자산이 모두 확인된 후 새 스냅샷 파일을 업로드한다.
5. 업로드 완료 후 로컬 프로젝트에 해당 Drive 스냅샷 ID를 기준점으로 저장한다.
6. 앱은 백업 완료 시각, 파일 크기, 포함 자산 수를 보여준다.

### 4.3 다른 PC에서 복원

1. 사용자가 같은 Google 계정으로 Drive를 연결한다.
2. 앱은 사용자 Drive 내 Subcast 백업 폴더에서 프로젝트와 분기 목록을 읽는다.
3. 사용자가 복원 대상과 스냅샷을 선택한다.
4. 앱은 압축 무결성, 체크섬, 스키마 버전, 필요한 자산을 검증한다.
5. 동명의 로컬 프로젝트가 있으면 덮어쓰지 않고 `가져온 프로젝트`로 새 로컬 ID를 만든다.
6. 기존 로컬 프로젝트가 복원 대상으로 선택된 경우에는 현재 로컬 상태를 먼저 자동 백업하고, 최종 교체 확인 후 적용한다.

### 4.4 동시 작업이 백업 충돌로 발견됨

예시: PC A와 PC B가 모두 Drive 스냅샷 S1을 내려받는다. A가 수정 후 S2를 백업하고, 이후 B도 S1에서 시작한 수정본을 백업한다.

1. B는 S1을 부모 스냅샷으로 가리키는 새 스냅샷을 별도 파일로 업로드한다. S2를 덮어쓰지 않는다.
2. 앱이 해당 프로젝트의 스냅샷 그래프를 다시 확인하면 S1에서 갈라진 두 작업을 발견한다.
3. B의 작업은 `프로젝트명 (분기 · PC 이름 · 시각)`으로 표시하고 A의 작업과 함께 목록에 남긴다.
4. 사용자에게 기본 프로젝트와 분기 프로젝트를 나란히 보여주고, 열기·이름 바꾸기·계속 백업하기를 제공한다.
5. 자동으로 어느 한쪽을 정본으로 승격하거나 병합하지 않는다.

초기 범위에서 동시 편집을 완전히 막지는 않는다. 오프라인 또는 미백업 작업을 서버가 알 방법이 없기 때문이다. 목표는 충돌을 사전에 모두 차단하는 것이 아니라, 업로드된 수정본을 보존하고 분기 상태를 명확하게 드러내는 것이다.

## 5. 데이터 및 저장 형식

### 5.1 백업 패키지

권장 형식은 `manifest.json`과 압축된 프로젝트 데이터, 자산 참조 목록을 담는 버전 있는 ZIP 패키지다. 데이터 JSON은 UTF-8로 정규화한 후 gzip 또는 ZIP 압축을 적용한다. 파일 확장자와 MIME 타입은 형식이 결정된 뒤 하나로 고정한다.

Manifest 필드 제안:

| 필드 | 목적 |
|---|---|
| `formatVersion` | 백업 컨테이너 형식 버전 |
| `projectId` | 기기별 로컬 ID와 독립된 클라우드 프로젝트 ID |
| `branchId` | 작업 계보를 구분하는 분기 ID |
| `snapshotId` | 스냅샷 고유 ID |
| `parentSnapshotId` | 이 스냅샷의 기준이 된 이전 스냅샷 |
| `createdAt` | 정렬과 사용자 표시용 UTC 시각 |
| `appVersion` / `schemaVersion` | 복원 호환성과 마이그레이션 판단 |
| `deviceId` / `deviceLabel` | 충돌 목록에서 작업 기기 식별 |
| `payloadSha256` | 프로젝트 페이로드 무결성 검증 |
| `assets[]` | 자산 ID, 역할, 크기, SHA-256, Drive 파일 ID |

사용자 이메일, 액세스 토큰, 개인 식별 정보는 백업 패키지에 포함하지 않는다. `deviceLabel`은 사용자 설정 이름을 쓰고 기본값은 `이 PC`로 하며, 계정의 Windows 사용자명은 자동 포함하지 않는다.

### 5.2 썸네일과 파생 데이터

- 슬라이드 썸네일은 백업 payload에서 제외한다.
- 복원 후 사용자가 보는 슬라이드부터 기존 프로그램의 캔버스 렌더러로 생성하고, 나머지는 백그라운드에서 생성한다.
- 로컬 썸네일 캐시는 canonical slide data hash, 관련 글꼴·렌더러 버전이 바뀔 때 무효화한다.
- Drive 백업에는 썸네일을 넣지 않아도 되며, 백업 목록 썸네일은 필요 시 로컬 생성 또는 낮은 우선순위의 별도 캐시로 처리한다.

샘플 측정에서 썸네일 제거 후 프로젝트 JSON 크기는 약 204~278KB였고, 같은 JSON을 gzip level 9로 압축하면 약 17.6~23.7KB였다. 이는 제공된 302~402장 샘플의 파일 측정치이며, 모든 프로젝트에 적용되는 보장값은 아니다. Supabase 용량 계산용 수치로 재사용하지 않는다.

### 5.3 미디어 및 글꼴 자산

- 배경 영상, 사용자 글꼴 바이너리, 슬라이드가 참조하는 이미지·오디오 등 파일 자산은 Drive의 Subcast 폴더에 별도 보관한다.
- 프로젝트 JSON의 `/static/backgrounds/<name>` 또는 `/static/fonts/<name>` 경로를 다른 PC에서도 안정적으로 찾을 수 있는 `assetId` 참조로 바꾸는 마이그레이션을 정의한다.
- 자산은 SHA-256을 계산해 계정 내 같은 파일 재업로드를 줄일 수 있다. 해시가 같더라도 기존 Drive 파일의 존재·휴지통 여부·크기를 확인한다.
- 파일명은 표시용이고, 자산의 정체성은 Drive 파일 ID와 체크섬으로 확인한다.
- 로컬 파일 경로만 있고 실제 자산이 없는 경우 백업을 실패 처리하거나 누락 목록을 보여준다. 깨진 참조를 정상 백업처럼 표시하지 않는다.
- 업로드 도중 실패하면 스냅샷을 완성본으로 등록하지 않는다. 재시도에서 이미 올라간 자산을 재사용하고 남은 항목만 올린다.

## 6. 분기 및 충돌 정책

### 6.1 변경 불가 스냅샷

각 백업은 새로운 Drive 파일로 생성한다. 같은 `snapshotId` 파일을 업데이트하지 않고, 마지막 버전 포인터 하나만 덮어쓰는 설계도 초기에는 사용하지 않는다. 스냅샷에는 부모 ID를 넣어 Drive 폴더 내 파일 목록으로 계보를 재구성한다.

그 결과 네트워크 지연 중 두 기기가 동시에 같은 부모를 확인하더라도 둘 다 새 파일로 저장할 수 있으며 어느 파일도 덮어쓰지 않는다. 이후 목록을 새로 읽을 때 같은 부모를 둔 자식 스냅샷이 둘 이상이면 충돌 분기로 표시한다. 이 방식은 안전한 보존을 우선하며, 분기 생성 시점이 즉시 동기화되지 않을 수 있다.

### 6.2 버전과 분기 표시

- 스냅샷은 분기별 순번과 생성 시각을 가진다.
- 분기명은 기본적으로 `기본 작업`, `분기 · <기기명> · <시각>`처럼 사람이 이해할 수 있게 만든다.
- 사용자가 분기를 선택하면 이후 백업은 해당 분기의 최신 스냅샷을 부모로 삼는다.
- 각 분기에는 원본 프로젝트 ID를 유지하되 로컬에서 가져올 때는 별도 로컬 프로젝트 ID를 발급한다.
- 분기 작업을 기존 기본 프로젝트로 자동 덮어씌우지 않는다.
- 초기에는 분기 간 자동 병합, Cherry-pick, 슬라이드 단위 diff를 제공하지 않는다.

### 6.3 Drive 동시 접근의 한계

Drive API는 파일 목록·파일 버전·수정 시각 등 메타데이터를 제공하지만, 이 기획은 하나의 중앙 데이터베이스가 제공하는 트랜잭션 잠금을 전제로 하지 않는다. 그래서 충돌 여부 확인과 업로드 사이에 다른 기기가 동시에 업로드하는 경합은 발생할 수 있다. 변경 불가 스냅샷과 부모 스냅샷 그래프는 그 상황에서도 데이터를 덮어쓰지 않게 하는 기본 보호 장치다. 이를 실시간 잠금 또는 완전한 단일 작성자 보장으로 표현하지 않는다.

Google Drive의 보존 가능한 개별 파일 revision 기능에 백업 정책을 의존하지 않는다. Subcast가 생성하는 고유 스냅샷 파일 자체가 복구 이력이 된다.

## 7. OAuth, 권한, 보안

- Windows 데스크톱 앱은 외부 브라우저를 이용하는 OAuth Authorization Code + PKCE 흐름을 사용한다. 클라이언트 시크릿을 EXE나 설정 파일에 넣지 않는다.
- Drive 권한은 앱이 생성하거나 사용자에게 선택된 파일에 제한하는 `drive.file` 중심으로 검토한다. 광범위한 `drive` 또는 `drive.readonly` 권한은 요청하지 않는다.
- `appDataFolder`는 앱 비공개 저장에 편리하지만, 사용자가 Drive에서 앱 연결을 제거하면 해당 폴더도 삭제될 수 있어 장기 백업의 기본 위치로 삼지 않는다.
- 토큰은 Windows Credential Manager 또는 Windows DPAPI로 보호한다. 일반 JSON 설정·로그·오류 보고서에 저장하지 않는다.
- 리프레시 토큰이 제공되지 않거나 만료·철회된 경우 재인증을 요구한다. 앱은 자체적으로 Google 토큰을 백엔드에 보내지 않는다.
- 권한을 취소해도 이미 Drive에 저장된 일반 폴더 백업 파일을 앱이 임의 삭제하지 않는다. 연결 해제는 로컬 토큰 제거와 상태 해제를 의미한다.
- Google은 비민감 범위도 기본 OAuth 앱 검증을 요구할 수 있다. 공개 배포 전 OAuth 동의 화면, 브랜드, 개인정보 처리방침, 테스트 계정 및 검증 필요 여부를 확인한다.

## 8. UI 및 상태 설계

### 메뉴

- 프로젝트 목록: 클라우드 백업 상태, 마지막 백업 시각, 충돌 분기 배지
- 프로젝트 메뉴: `클라우드 백업`, `클라우드에서 복원`, `백업 이력`, `Drive 연결 관리`
- 설정: Drive 연결 계정 표시, 연결 해제, 기기 이름, 백업 폴더 열기

### 사용자가 구분할 상태

1. `연결 안 됨`: Drive 연결 필요
2. `로컬 변경 있음`: 마지막 백업 이후 로컬 수정 존재
3. `업로드 중`: 진행률·취소 가능 여부 표시
4. `백업 완료`: 스냅샷 ID·시각 확인 가능
5. `클라우드에 새 버전 있음`: 현재 로컬 기준보다 새로운 스냅샷 존재
6. `충돌 분기 있음`: 어느 작업도 삭제되지 않았으며 선택이 필요함
7. `자산 누락`: 영상·글꼴 등 일부 파일을 찾지 못함
8. `인증 필요`: 계정 재연결 필요
9. `Drive 용량 부족`: 업로드를 중단하고 해결 안내
10. `오프라인`: 로컬 저장은 계속되며 클라우드 백업은 대기

### 편집 안내

프로젝트 편집 시작 시 한 번 다음 취지의 안내를 표시한다: “여러 PC에서 동시에 편집하면 작업이 분기될 수 있습니다. 백업을 마친 뒤 다른 PC에서 여세요.” 매번 확인 버튼을 강제하지 않고, 충돌 분기가 발견되면 구체적으로 어느 스냅샷에서 갈라졌는지 보여준다.

## 9. 복원 및 기존 데이터 호환

- 기존 `.json` 프로젝트 내보내기/가져오기는 계속 지원한다. 클라우드 백업은 별도의 버전 있는 압축 포맷으로 추가한다.
- 옛 JSON 백업을 Drive에서 가져오는 경우 이전 포맷을 감지하고 현재 ProjectData 스키마로 변환한 뒤 새 클라우드 스냅샷으로 저장할 수 있어야 한다.
- 프로젝트 스키마 버전이 앱보다 높으면 자동으로 낮은 버전으로 변환하지 않고 복원 불가 이유를 표시한다.
- 복원 전에 현재 프로젝트를 로컬 임시 복구 지점으로 저장한다.
- 자산 다운로드와 체크섬 검증이 모두 성공한 다음에만 프로젝트 데이터 참조를 적용한다.
- 적용 중 실패하면 현재 로컬 프로젝트를 유지하고 임시 파일을 정리한다.
- 클라우드 projectId와 로컬 projectId를 분리해 여러 PC에서 같은 클라우드 프로젝트를 독립적으로 가져와도 ID 충돌이 없게 한다.

## 10. 단계별 개발 제안

### 단계 0: 데이터 범위 인벤토리

프로젝트 JSON이 참조하는 모든 파일 경로와 글로벌 저장 항목을 수집한다. 배경 영상, customFonts, 슬라이드 이미지, templates, praise/song data, tags, monitor config의 포함 여부를 확정한다. 이 단계 전에는 “전체 데이터 백업”이라고 표시하지 않는다.

### 단계 1: 백업 포맷과 무결성

썸네일 제거, 압축, manifest, SHA-256, 스키마 버전, 기존 JSON 변환을 구현한다. 로컬 파일만으로 압축·해제·손상 감지를 테스트한다. 기존 가져오기 동작을 회귀 검증한다.

### 단계 2: Drive 연결 및 수동 스냅샷

OAuth, 안전한 토큰 저장, Drive 폴더, 프로젝트 스냅샷 업로드·목록·다운로드를 붙인다. 자산보다 스냅샷을 먼저 완성 상태로 보여주지 않는 순서를 보장한다.

### 단계 3: 자산 업로드·복원

프로젝트의 로컬 자산을 manifest에 연결하고, 누락·중복·업로드 실패·재시도·용량 부족을 처리한다. 복원 후 다른 PC에서도 경로가 유효한지 확인한다.

### 단계 4: 분기 감지 및 UX

부모 스냅샷 그래프를 계산하고 같은 부모의 여러 수정 스냅샷을 분기로 표시한다. 사용자가 분기 선택·이름 변경·계속 작업·복원할 수 있게 한다. 삭제 또는 병합은 별도 기능으로 두고 초기 자동 동작에 넣지 않는다.

### 단계 5: 배포 및 운영 준비

Google OAuth 동의 화면 검증, 개인정보 처리방침, 토큰 제거·재인증, 설치·업데이트 데이터 보존, 오래된 백업 정리 UX를 검증한다. 자동 정리로 사용자의 유일한 백업을 지우지 않는다.

## 11. 검증 시나리오 및 완료 기준

### 핵심 회귀 시나리오

- 작은 프로젝트와 400장 이상 프로젝트의 백업·복원 후 요소·스타일·순서·템플릿·설정이 일치한다.
- 썸네일 없는 스냅샷 복원 후 썸네일이 생성되고, 내용이 바뀌면 캐시가 무효화된다.
- 사용자 글꼴과 영상·이미지 자산이 다른 PC에 복원된 뒤 정상 표시된다.
- 자산 업로드 중 앱 종료·네트워크 단절 후 재시도하면 중복 자산 없이 완료된다.
- 파일이 잘렸거나 체크섬이 다르면 프로젝트를 적용하지 않는다.
- Drive 권한 거부, 권한 철회, 토큰 만료, 저장 공간 부족, API 제한, 오프라인 상태에 오류 안내를 표시한다.
- A와 B가 같은 부모 스냅샷을 바탕으로 각각 백업하면 두 스냅샷이 모두 남고 충돌 분기로 나타난다.
- 복원 중 오류가 나도 기존 로컬 프로젝트가 보존되고 로컬 복구 지점으로 돌아갈 수 있다.
- 앱 연결 해제·재연결 후 Drive 데이터가 자동 삭제되지 않고 다시 목록에 나타난다.
- 기존 `.json` 프로젝트 가져오기와 설치 업데이트 후 데이터 보존 테스트가 통과한다.

### 제품 완료 기준

1. 어떤 정상·실패 경로에서도 다른 기기의 스냅샷을 덮어써서 사라지게 하지 않는다.
2. 백업 완료 표시 전까지 스냅샷과 모든 필수 자산의 업로드 및 체크섬을 검증한다.
3. 복원은 기존 로컬 데이터 보호 지점을 만든 뒤 원자적으로 적용한다.
4. 충돌 분기는 기본 프로젝트와 구별되고, 이름·기기·시각·부모 스냅샷을 확인할 수 있다.
5. 민감한 OAuth 토큰이 평문 파일과 로그에 남지 않는다.
6. 썸네일 제거가 서버 저장량과 전송량에서 측정 가능하게 반영된다.
7. 실시간 동기화나 자동 병합을 지원한다고 오해할 UI 문구가 없다.

## 12. 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 프로젝트가 로컬 자산 경로를 직접 참조 | 다른 PC에서 영상·글꼴이 깨짐 | 안정된 assetId 도입 및 자산 사전 검사 |
| Drive 업로드 중 일부 파일만 성공 | 잘못된 복원 또는 고아 파일 | 자산 우선, manifest 검증 후 스냅샷 등록, 재시도와 정리 도구 |
| 같은 부모로 동시 업로드 | 작업 계보가 일시적으로 분기 | immutable snapshot, 부모 ID 그래프 재조회, 덮어쓰기 금지 |
| 사용자가 Drive에서 백업 삭제 | 복원 지점 손실 | 앱에서 삭제 영향 설명, 삭제 시 프로젝트·자산 참조 검사, 기본 자동 삭제 금지 |
| OAuth 검증·권한 동의 부담 | 출시 지연 또는 경고 화면 | 최소 scope, 공개 배포 전 브랜드·검증 준비 |
| 토큰 유출 | 사용자 Drive 데이터 접근 | OS 보안 저장소, 최소 scope, 로그 마스킹, 재인증·연결 해제 경로 |
| Google 계정/Drive 장애·한도 | 백업 지연 | 로컬 앱 사용 지속, 재시도 가능 상태, 사용자 데이터 로컬 보존 |
| 스키마 변경 | 오래된 백업 복원 실패 | 명시적 schemaVersion과 마이그레이션 테스트 |
| 분기가 많아져 프로젝트 목록 혼란 | 사용자가 정본을 찾기 어려움 | 기본/분기 묶음 표시, 기기·시각·부모 표시, 명확한 이름 변경 |

## 13. 미결정 사항

아래는 구현 전에 제품 결정이 필요하다. 본 문서의 기본 제안은 괄호 안과 같다.

1. 초기 백업 범위: 프로젝트 및 참조 자산만 포함할지, 찬양곡 DB·태그·전역 템플릿도 별도 포함할지 (프로젝트 및 자산만)
2. 백업 시점: 사용자 수동 백업만 제공할지, 로컬 저장 뒤 자동으로 Drive 업로드할지 (수동 백업만)
3. 충돌 분기 생성: 충돌 감지 즉시 자동 분기를 만들지, 업로드는 보존하되 사용자 확인 후 분기 이름을 확정할지 (자동 보존 및 자동 분기 표시)
4. Drive 저장 위치: 사용자가 볼 수 있는 `Subcast` 폴더 또는 숨김 `appDataFolder` (사용자에게 보이는 폴더)
5. 과거 버전 보관: 무제한 보관 또는 앱 내 보관 개수 제한 (초기 자동 삭제 없음, 수동 정리)
6. 암호화: Google Drive 암호화 외에 앱 암호화·암호 설정을 추가할지 (초기에는 추가 비밀번호 없음, 향후 위협 모델 검토)
7. 사용자 명칭: 분기 프로젝트를 기본 프로젝트 목록에 별도 노출할지 묶음 하위 항목으로 표시할지 (프로젝트 목록에서 원본 아래 분기로 묶음)
