# Subcast 사용자 시나리오 테스트 명세

- 작성일: 2026-10-09
- 상태: 소스 기반 제안 명세. 테스트 구현 및 앱 실행 검증 전.
- 목적: 업데이트마다 기존 사용자 기능의 손상, 데이터 유실, 화면 간 불일치를 발견한다.
- 범위: 프로젝트, 편집, 자료 관리, 송출, 모니터, 실행 및 업데이트. `archive/`는 조사하지 않았다.
- 원칙: 아래 기대 결과는 검증할 기준이며 현재 앱이 이미 만족한다는 뜻이 아니다. 기능 목록의 각 변형은 독립 테스트로 실행한다.

## 실행 및 판정 규칙

### 공통 준비 데이터

- 모든 실행은 별도 테스트 데이터 폴더 및 격리된 Windows 테스트 계정을 사용한다. 실제 사용자 AppData, 프로젝트, 송출 장비를 수정하지 않는다.
- 프로젝트 A: 일반 슬라이드 3장, 찬양 2곡, 성경 구절, 빈 슬라이드, 템플릿, 사용자 글꼴을 포함한다. 프로젝트 B는 내용과 설정이 다른 비교 대상이다.
- 곡 A: 한글 제목, 3개 단락, 명시적 빈 화면, 분위기 태그. 곡 B: 긴 가사와 다른 분위기. 자료는 가공한 자체 테스트 문구를 사용한다.
- 배경 V1/V2: 짧고 구분 가능한 정상 영상, 태그별 영상, 기본 배경. 손상 파일과 큰 파일은 별도 준비한다. 이미지 I1 및 다운로드 가능한 테스트 글꼴도 준비한다.
- 성경 데이터는 테스트 환경의 실제 제공 역본을 사용한다. 기대 본문을 테스트 시작 전에 고정하고, 화면 결과를 그대로 정답으로 복사하지 않는다.
- 화면 이름: 목록=프로젝트 목록, 편집=편집기, 제어=송출 제어, 방송=방송 뷰어, 현장=배경 포함 현장 뷰어, 모니터=무대 모니터.
- 기본 화면 크기는 1920×1080. 화면 크기 변형은 1280×720, 1024×768을 별도로 실행한다. 이는 테스트 조건이며 지원 범위를 새로 선언하지 않는다.

### 각 테스트가 남겨야 할 기록

- 시나리오 ID, 변형 이름, 앱 버전, 실행 환경, 준비 데이터 버전, 시작/종료 시각.
- 기대 값과 실제 값, 실패 단계, 화면 캡처, 브라우저 오류, 서버 로그, 관련 요청 및 WebSocket 기록.
- 데이터 검증은 화면 표시 외에도 내보낸 프로젝트/API 조회/독립 저장 데이터 조회로 확인한다. ID와 생성 시각처럼 새로 생성되는 값은 별도 비교한다.
- 캔버스는 DOM 글자 검사만으로 판정하지 않는다. 객체 속성, 렌더링 화면, 독립 저장 데이터에서 목적에 맞는 증거를 수집한다.
- 결과는 `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN`으로 구분한다. 준비 실패, 미지원 환경, 정책 미확정은 통과로 처리하지 않는다.
- 고정 대기 대신 저장 응답, 파일 생성, 화면 갱신 등 완료 조건을 기다린다. 무한 대기는 금지하며 시간 제한 초과는 증거를 남긴다.
- 실행용 시간 제한과 기능 성능 기준은 구분한다. 아직 합의하지 않은 송출 지연 목표를 임의로 통과 기준으로 만들지 않는다.
- 실패 후 재실행이 통과해도 최초 실패 기록을 보존하고 불안정 테스트 또는 환경 문제로 분류한다.
- 각 사례 전 초기 상태를 복원한다. 여러 테스트가 같은 프로젝트·태그·영상·클립보드를 동시에 수정하지 않는다.

### 방식과 우선순위

- `브라우저+데이터`: 실제 UI 조작과 서버/저장 데이터 대조. 자동화 후보이며 아직 구현되지 않았다.
- `장애 주입`: API 실패, 응답 지연, 연결 차단, 파일 오류를 통제한 환경에서 재현한다.
- `Windows`: 설치, 트레이, 파일 대화상자, 글꼴/권한, 디스플레이 환경이 필요하다.
- `장비`: 실제 영상 출력·OBS·스위처를 검사한다. 브라우저만으로 통과를 선언할 수 없다.
- `P0`: 데이터 유실, 핵심 송출, 업데이트 데이터 유지. 개발 후 핵심 검증 후보.
- `P1`: 기능별 정상 및 예외 검증. 전체 회귀 실행에 포함.
- `P2`: 화면/장비/설치 환경 검증. 해당 환경에서 배포 전 실행.

## 01. 프로젝트 관리

근거: `frontend/js/index.js`, `backend/routers/projects.py`.

### SC-01-01 프로젝트 생성과 재실행 [P0]
- 준비: 격리된 목록 화면, 프로젝트 이름 `테스트 예배 A`.
- 절차: 생성 → 편집 열기 → 일반 슬라이드 저장 → 서버와 브라우저 종료 → 재시작.
- 기대: 목록과 편집에서 이름·슬라이드가 일치하고 저장 내용이 유지된다. 생성은 한 번만 이루어진다.
- 검증: 목록·편집, 프로젝트 목록 및 내보내기. 방식: 브라우저+데이터.

### SC-01-02 프로젝트 전환과 데이터 분리 [P0]
- 준비: 내용이 다른 A/B, A에 저장 완료된 변경.
- 절차: A → B 전환 → B 수정·저장 → A 복귀 → 재시작.
- 기대: 현재 프로젝트 표시와 열린 화면 상태가 일치한다. A/B 내용·설정이 서로 덮어써지지 않는다.
- 검증: 목록·편집·제어·뷰어, A/B 내보내기. 방식: 브라우저+데이터.

### SC-01-03 이름 변경과 입력 검증 [P1]
- 준비: A/B, 원래 이름 목록을 기록한다.
- 절차: 더블 클릭 이름 변경·확정·취소; 새 프로젝트 이름에 빈 문자열·공백·기존 이름을 각각 입력.
- 기대: 확정한 이름만 저장되고 취소·거부한 입력은 기존 데이터를 바꾸지 않는다. 현재 코드의 이름 중복 정책과 안내가 일치한다.
- 검증: 목록·편집, 재조회. 방식: 브라우저+데이터. 변형은 독립 실행.

### SC-01-04 단일·다중 프로젝트 복제 [P1]
- 준비: 요소와 설정을 포함한 A/B.
- 절차: 한 개 또는 두 개 선택 → 복사·붙여넣기 → 복제본 편집·저장.
- 기대: 선택한 개수만 복제되고 새 ID를 가진다. 원본 내용·설정이 유지되며 복제본 수정이 원본에 영향을 주지 않는다.
- 검증: 목록, 원본/복제본 내보내기. 방식: 브라우저+데이터.

### SC-01-05 프로젝트 삭제와 현재 프로젝트 처리 [P1]
- 준비: A/B와 현재 작업 프로젝트 기록.
- 절차: 삭제 취소, 비활성 프로젝트 단일 삭제, 다중 삭제, 현재 프로젝트 삭제를 각각 실행.
- 기대: 취소 시 변화가 없고 확정 시 선택한 대상만 제거된다. 현재 프로젝트 삭제 후 모든 화면은 같은 유효 프로젝트 또는 일관된 빈 상태를 사용한다.
- 검증: 목록·편집·제어·뷰어, 재시작. 방식: 브라우저+데이터. 마지막 프로젝트 처리 정책은 아래 정책 항목 참조.

## 02. 프로젝트 내보내기·가져오기

근거: `frontend/js/index.js`, `backend/routers/projects.py`, `backend/services/project_import_tags.py`.

### SC-02-01 단일·다중 프로젝트 왕복 [P0]
- 준비: A/B의 독립 기준 데이터, 각 프로젝트의 요소·순서·설정·태그.
- 절차: 단일 또는 다중 내보내기 → 격리된 새 환경에서 가져오기 → 열기·재시작.
- 기대: 내보낸 개수와 가져온 개수가 같다. 새 ID/시각을 제외한 의미 있는 내용이 기준과 일치한다. 외부 파일 의존성은 별도로 보고한다.
- 검증: 다운로드 파일, 목록·편집·뷰어, 재내보내기. 방식: 브라우저+데이터.

### SC-02-02 동일 파일 반복 가져오기 [P1]
- 준비: A의 내보내기 파일, 기존 A를 기록.
- 절차: 같은 파일을 두 번 가져오기 → 한 가져온 프로젝트만 수정.
- 기대: 기존 프로젝트를 의도치 않게 덮어쓰지 않고 프로젝트 식별자가 충돌하지 않는다. 수정은 해당 프로젝트에만 반영된다.
- 검증: 목록 및 각 프로젝트 내보내기. 방식: 브라우저+데이터.

### SC-02-03 외부 태그 연결과 규칙 재사용 [P0]
- 준비: 외부 태그 `외부잔잔`, 로컬 태그 `잔잔`, 로컬 배경 V1.
- 절차: 가져오기에서 태그 연결 지정 → 슬라이드 송출 → 같은 외부 태그 파일을 다시 가져오기.
- 기대: 슬라이드에 로컬 표준 태그가 저장되고 로컬 배경 선택 규칙이 적용된다. 저장한 연결 규칙이 다음 가져오기 선택에 반영된다.
- 검증: 연결 창·편집·현장, 매핑 조회 및 내보내기. 방식: 브라우저+데이터.

### SC-02-04 가져오기 취소와 태그 없는 파일 [P1]
- 준비: 태그 있는 파일/없는 파일, 기존 프로젝트 목록.
- 절차: 연결 창에서 취소; 태그 없는 파일은 설명 확인 후 가져오기.
- 기대: 취소는 프로젝트·연결 규칙을 바꾸지 않는다. 태그 없는 파일은 내용이 유지되고 현재 환경 배경 설정과 충돌하지 않는다.
- 검증: 목록·연결 창·현장, 매핑 조회. 방식: 브라우저+데이터.

### SC-02-05 잘못된 파일과 자산 의존성 [P0]
- 준비: JSON 문법 오류, 잘못된 자료형, 잘못된 슬라이드 구조, 현재 PC에 없는 이미지/영상/글꼴 참조.
- 절차: 각 파일을 별도 초기 상태에서 가져오기 → 안내 확인 → 기존 프로젝트 다시 열기.
- 기대: 거부한 파일은 성공으로 표시하지 않고 기존 데이터를 손상시키지 않는다. 파일 참조를 가져온 경우 누락 자산을 정상 자산으로 표시하지 않는다.
- 검증: 목록·편집·뷰어, 오류 응답 및 저장 데이터. 방식: 브라우저+데이터. 다중 파일 일부 실패와 누락 자산 정책은 정책 항목 참조.

## 03. 슬라이드 관리

근거: `frontend/js/modules/editor-slides.js`, `backend/services/websocket_handler.py`.

### SC-03-01 생성·이름 변경·이동 후 복원 [P0]
- 준비: A의 일반 슬라이드 3장.
- 절차: 선택 슬라이드 뒤에 추가 → 이름·본문 수정 → 다른 슬라이드 선택 → 복귀 → 재시작.
- 기대: 추가 위치·이름·본문이 유지되고 슬라이드 수가 한 장만 증가한다.
- 검증: 편집·제어, 내보내기. 방식: 브라우저+데이터.

### SC-03-02 단일·복수·범위 선택 [P1]
- 준비: 슬라이드 6장, 선택을 초기화한다.
- 절차: 클릭, Ctrl 클릭, Shift 클릭으로 지정한 ID 집합을 선택하고 선택 해제한다.
- 기대: 표시된 선택과 내부 선택 대상이 일치하며 이후 복사/삭제가 그 집합에만 적용된다.
- 검증: 편집 목록·전체 보기. 방식: 브라우저+데이터.

### SC-03-03 단일·다중 순서 변경 [P0]
- 준비: ID와 순서가 고정된 6장, 중간 2장 선택.
- 절차: 한 장 또는 선택 묶음을 앞·뒤로 드래그 → 제어에서 순차 이동 → 재시작.
- 기대: 의도한 순서, 묶음 내부 순서, 슬라이드 내용이 유지된다. 편집·송출·저장 순서가 같다.
- 검증: 편집·제어·뷰어, 내보내기. 방식: 브라우저+데이터.

### SC-03-04 전체 보기 조작 [P1]
- 준비: 찬양 그룹과 일반 슬라이드가 있는 A.
- 절차: 전체 보기 열기 → 확대·축소 및 그룹 표시 조작 → 선택·재정렬 → 닫기.
- 기대: 일반 목록과 같은 슬라이드가 선택되고 순서가 일치한다. 표시 변경만으로 내용이나 찬양 그룹 정보가 바뀌지 않는다.
- 검증: 편집 전체 보기·일반 목록, 내보내기. 방식: 브라우저+데이터.

### SC-03-05 삭제 경계 조건 [P0]
- 준비: 일반·편집 중·송출 중·마지막 한 장 조건을 각각 준비.
- 절차: 삭제 취소 및 확정 → 각 화면 상태 확인 → 재시작.
- 기대: 취소 시 변화가 없고 대상만 삭제된다. 삭제한 ID에 대한 선택·잠금·송출 참조가 남아 오류를 일으키지 않는다.
- 검증: 편집·제어·전체 뷰어, 내보내기. 방식: 브라우저+데이터. 송출 중/마지막 삭제의 표시 정책은 정책 항목 참조.

## 04. 캔버스 요소 편집

근거: `frontend/js/modules/editor-elements.js`, `editor-canvas.js`, `editor-init.js`, `backend/schemas.py`.

### SC-04-01 제목·부제·본문 스타일 [P1]
- 준비: 빈 일반 슬라이드, 구분 가능한 자체 문구.

- 기대: 각 UI가 제공하는 스타일 값과 내용이 저장/복원되고 편집·뷰어 표시가 일치한다.
- 검증: 편집·방송·현장, 요소 속성 및 내보내기. 방식: 브라우저+데이터. 글자 종류별 독립 실행.

### SC-04-02 도형 종류별 속성 [P1]
- 준비: 빈 슬라이드. 종류: 사각형·원·삼각형·선.
- 절차: 종류별 추가 → 지원 속성인 크기·채움·테두리·불투명도·모서리 등을 변경 → 저장·재열기.
- 기대: 해당 도형에 지원되는 값이 유지되고 다른 요소가 바뀌지 않는다. 지원하지 않는 속성은 별도 기능으로 가정하지 않는다.
- 검증: 편집·뷰어, 내보내기. 방식: 브라우저+데이터.

### SC-04-03 이미지 삽입 [P1]

- 절차: 파일 선택 또는 끌어놓기로 삽입 → 이동·크기 변경 → 저장·재실행.
- 기대: 한 번 삽입되고 위치·크기·이미지가 유지된다. 파일 선택 취소는 요소를 추가하지 않는다.
- 검증: 편집·뷰어, 자산 요청 및 내보내기. 방식: 브라우저+데이터/파일 입력.

### SC-04-04 좌표·크기·정렬·레이어 [P1]
- 준비: 겹친 글자·도형·이미지, 각 초기 위치 기록.
- 절차: 좌표/크기 직접 입력 및 드래그 → 정렬 버튼별 적용 → 앞뒤 순서 변경 → 저장.
- 기대: 선택 요소만 의도한 위치·크기·순서로 바뀌고 가려짐 순서가 뷰어와 일치한다.
- 검증: 편집 캔버스·레이어 목록·뷰어, 내보내기. 방식: 브라우저+데이터. 정렬/레이어 버튼별 독립 실행.

### SC-04-05 그룹화·해제·다중 편집 [P1]
- 준비: 위치와 스타일이 다른 3개 요소.
- 절차: 다중 선택 → 그룹화 → 이동·크기 변경 → 저장·재열기 → 해제 → 하나만 수정.
- 기대: 그룹의 상대 배치와 개별 스타일이 유지된다. 해제 후 독립 편집 가능하고 요소가 누락/중복되지 않는다.
- 검증: 편집·뷰어, 그룹 자식 데이터. 방식: 브라우저+데이터.

### SC-04-06 긴 글자와 외곽선 렌더링 [P1]
- 준비: 긴 한글·여러 줄·특수문자·다른 굵기의 외곽선 문구.
- 절차: 크기·줄바꿈·외곽선 변경 → 각 테스트 화면 크기에서 편집/송출 → 재열기.
- 기대: 저장 본문이 손상되지 않고 외곽선이 글자 내부를 의도치 않게 가리지 않는다. 의도한 글상자 내부 문구가 잘리거나 다른 요소에 예기치 않게 겹치지 않는다.
- 검증: 편집·방송·현장 캡처, 글상자 속성. 방식: 브라우저+데이터/시각 비교.

## 05. 저장·히스토리·클립보드

### SC-05-01 자동·수동 저장 [P0]

- 검증: 편집 상태 표시, 독립 내보내기. 방식: 브라우저+데이터.

### SC-05-02 수정 직후 이동 [P0]

- 기대: 정상 저장된 마지막 수정이 유지된다. 실패가 있으면 실패로 알리고 다른 대상에 잘못 저장하지 않는다.
- 검증: 편집·목록, A/B 내보내기. 방식: 브라우저+데이터. 슬라이드/프로젝트 이동 별도 실행.

### SC-05-03 실행 취소·다시 실행·취소 버튼 [P1]
- 준비: 저장한 기준 슬라이드.
- 절차: 글자 수정·요소 이동·추가·삭제 각각 실행 취소/다시 실행; 별도 실행에서 미적용 변경 후 취소 버튼 사용.
- 기대: 히스토리 단계의 내용·위치·요소 수가 복원된다. 취소 버튼은 확정된 저장 상태를 기준으로 동작하며 다른 슬라이드에 영향을 주지 않는다.
- 검증: 편집·내보내기. 방식: 브라우저+데이터. 자동 저장 이후 취소 범위는 정책 항목 참조.

### SC-05-04 슬라이드 복사·잘라내기·붙여넣기 [P0]
- 준비: 일반·찬양·빈 슬라이드, 태그·곡 그룹·직접 지정 배경 정보.
- 절차: 단일/다중 복사 또는 잘라내기 → 붙여넣기 → 저장·재열기.
- 기대: 새 ID와 의도한 순서를 가진다. 내용·태그·배경 메타데이터가 유지되고 원본과 복제본 수정은 분리된다. 곡 그룹 복제 범위는 정책에 따른다.
- 검증: 편집·제어·현장, 내보내기. 방식: 브라우저+데이터.

### SC-05-05 요소 클립보드와 잘못된 입력 [P1]
- 준비: 단일/다중/그룹 요소, 일반 문자열·잘못된 JSON 클립보드, 클립보드 권한 거부 환경.
- 절차: 요소 복사·잘라내기·붙여넣기; 잘못된 자료 붙여넣기; 클립보드 쓰기 실패 주입.
- 기대: 정상 자료의 좌표·스타일·그룹이 유지된다. 잘못된 자료는 대상 데이터를 손상시키지 않으며 실패한 잘라내기로 원본이 유실되지 않는다.
- 검증: 편집·클립보드·내보내기. 방식: 브라우저+데이터/장애 주입.

### SC-05-06 저장 실패·응답 지연·연결 복구 [P0]
- 준비: 기준 저장 데이터, WebSocket 응답을 차단 가능한 환경.
- 절차: 저장 응답 지연/서버 오류/연결 끊김 각각 주입 → 상태 확인 → 복구 → 재조회.
- 기대: 응답 확인 전 완료로 판정하지 않는다. 실패는 표시되고 기존 저장 데이터가 손상되지 않는다. 현재 코드의 저장 응답 대기 한도 10초에 따른 실패를 기록한다.
- 검증: 편집 상태, 요청/응답, 독립 내보내기. 방식: 장애 주입. 미저장 변경의 자동 복구 여부는 정책 항목 참조.

- 기대: 제목·가사·태그가 유지되고 중복 처리 안내의 건수가 실제 결과와 같다. 실패한 잘라내기로 원본을 잃지 않는다.

### SC-07-07 삭제 취소·단일·다중 삭제 [P1]

### SC-07-08 선택·전체 자료 왕복 [P1]

- 절차: 앱 업데이트 실행 → 저장 처리·백업 생성·설치 순서 관찰 → 새 버전 실행 → 백업 내용 조회.
- 기대: 업데이트 전 저장 처리와 백업의 성공/실패가 분명하고 백업이 읽을 수 있다. 저장 실패 상태를 무시하고 데이터 안전을 성공으로 선언하지 않는다.
- 검증: 편집 상태·업데이트 상태·백업 파일·새 버전 내보내기. 방식: Windows+데이터/장애 주입. 미저장 데이터 정책은 정책 항목 참조.

### SC-16-07 다운로드 검증과 설치 중단 [P0]
- 준비: 다운로드 실패·검증값 불일치·미신뢰 URL·잘못된 검증 파일 응답.
- 절차: 각 조건에서 자동 업데이트 실행 → 설치 프로세스 생성 여부·기존 앱 데이터 확인.
- 기대: 검증되지 않은 설치 파일을 실행하지 않고 실패 원인을 표시/기록한다. 기존 앱·데이터를 손상시키지 않는다.
- 검증: 목록·트레이·로그·프로세스·시험 데이터. 방식: Windows+장애 주입.

### SC-16-08 기존 저장 위치 이전과 재시작 [P0]
- 준비: 과거 설치 위치의 사용자 DB/파일과 AppData의 기존 사용자 데이터. 복사 실패 조건도 별도 준비.
- 절차: 새 버전 실행 → 이전 결과 확인 → 다시 실행; 별도 실행에서 이전 실패 주입.
- 기대: 기존 AppData 데이터가 덮어써지지 않고 이전은 반복해도 중복/유실을 만들지 않는다. 실패 시 원본 데이터가 보존되고 실패를 성공으로 표시하지 않는다.
- 검증: 시험 DB·파일·설정 비교, 시작 로그. 방식: Windows+데이터/장애 주입.

### SC-16-09 설치 후 계정·버전·캐시 [P0]
- 준비: 일반 사용자 계정에서 시작한 업데이트, 관리자 권한이 필요한 설치 환경, 이전 화면 캐시.
- 절차: 업데이트 → 자동 재실행 또는 안내된 수동 실행 → 열린 화면·데이터 폴더·버전 확인.
- 기대: 기존 사용자 계정의 데이터를 사용한다. 다른 관리자 계정의 빈 데이터로 대체하지 않으며 화면과 서버 버전이 새 버전으로 일치한다. 자동 실행 조건은 설치 스크립트의 현재 분기를 따른다.
- 검증: Windows 사용자/프로세스·버전·목록·자산 요청. 방식: Windows+데이터.

## 17. 실제 사용 흐름 통합 검증

개별 기능 테스트를 대체하지 않는다. 서로 다른 기능을 연결했을 때의 상태와 데이터 연속성을 검증한다.

### SC-17-01 예배 준비 후 재실행 [P0]
- 준비: 새 프로젝트, 곡 A/B, 성경 본문, 템플릿, 태그별 배경.
- 절차: 생성 → 찬양/성경 추가 → 디자인·빈 화면·배경 지정 → 순서 정리 → 저장 → 앱 종료·재실행.
- 기대: 전체 슬라이드 순서·내용·디자인·태그·배경 지정이 유지되고 제어 화면에서 그대로 진행할 수 있다.
- 검증: 목록·편집·제어·내보내기. 방식: 브라우저+데이터.

### SC-17-02 실제 진행 중 수정 [P0]
- 준비: SC-17-01의 준비 결과를 독립 복원, 방송·현장·모니터.
- 절차: 찬양 → 빈 화면 → 성경 → 다음 찬양; 송출 중 가사 수정·저장 및 배경 변경.
- 기대: 선택한 내용이 각 채널 규칙대로 출력되고 모니터 현재/다음 표시가 순서와 일치한다. 이전 곡 자막·배경이 의도치 않게 남지 않는다.
- 검증: 편집·제어·세 출력 화면·저장 데이터. 방식: 브라우저+데이터.

### SC-17-03 다른 PC로 프로젝트 이동 [P0]
- 준비: PC A 내보내기 파일, 태그·배경·글꼴 구성이 다른 격리 PC B.
- 절차: 내보내기 → B 가져오기 → 태그 연결·필요 자산 준비 → 편집 → 송출 → 재시작.
- 기대: 프로젝트 본문과 순서가 유지된다. 로컬 자산 연결과 누락이 구분되며 가져오기 결과가 실제 사용 가능한지 확인된다.
- 검증: 양 PC 내보내기·편집·출력. 방식: Windows+브라우저+데이터.

### SC-17-04 연결 장애 후 작업 재개 [P0]
- 준비: 진행 중 프로젝트, 저장 완료 상태와 미저장 변경을 각각 준비.
- 절차: 서버/연결 중단 → 안내·뷰어 상태 기록 → 연결 복구 → 현재 프로젝트·슬라이드 재조회 → 작업 재개.
- 기대: 복구된 화면은 같은 서버 상태를 사용하고 기존 저장 데이터가 유지된다. 미저장 변경은 실제 복구 여부를 구분하며 오래된 상태로 덮어쓰지 않는다.
- 검증: 편집·제어·전체 출력·로그·내보내기. 방식: 장애 주입.

### SC-17-05 이전 버전에서 업데이트 후 예배 진행 [P0]
- 준비: 이전 버전에서 만든 예배 프로젝트와 별도 기준 기록.
- 절차: 실제 설치 업데이트 → 기존 프로젝트 열기 → 찬양/성경/빈 화면 송출 → 수정·저장 → 재실행.
- 기대: 업데이트 직후뿐 아니라 수정·재저장 이후에도 데이터와 기능이 유지된다. 화면·서버·사용자 데이터 계정이 일치한다.
- 검증: 설치 앱·모든 주요 화면·DB/파일/내보내기. 방식: Windows+브라우저+데이터.

## 자동화 전에 확정하거나 기준으로 기록할 정책

이 항목은 기능 변경을 승인받은 내용이 아니다. 구현된 현재 정책을 먼저 확인하고, 선택이 필요한 항목만 별도로 결정한다. 미확정 기대 결과는 BLOCKED로 기록한다.

1. 현재 송출 중 슬라이드를 삭제하거나 마지막 프로젝트/슬라이드를 삭제했을 때 출력과 선택을 무엇으로 전환할지.
2. 자동 저장 완료 이후 취소 버튼이 되돌리는 범위, 연결 복구 시 미저장 변경의 복구/폐기 및 사용자 안내.
3. 다른 프로젝트로 복제한 찬양 슬라이드의 곡 그룹 범위, 그룹의 일부만 복사했을 때 배경 전체 적용 범위.
4. 다중 프로젝트 가져오기 중 일부 항목 실패 시 전체 취소 또는 부분 성공을 표시하는 정책.
5. 가져온 파일에 없는 로컬 이미지/영상/글꼴, 재생 불가 영상에 대한 대체 표시 및 안내.
6. 송출 반영 지연·업로드·검색 등 성능 기준과 실행 환경별 허용치. 실행 타임아웃을 성능 목표로 간주하지 않는다.
7. 여러 후보 영상이 자동 매칭되는 경우 정확한 한 파일 선택을 보장할지, 유효 후보 집합 내 선택을 검사할지. 랜덤 조건은 통제한다.

## 기능과 시나리오 연결 유지

- 01~16은 기능별 회귀 사례, 17은 전체 사용 흐름이다. 각 하위 ID의 변형은 `SC-04-02/rect`처럼 식별한다.
- 새 기능이나 새 컨트롤을 추가할 때 소스 위치·사용자 행동·관련 시나리오 ID를 함께 추가한다. 버튼/메뉴, API, WebSocket 메시지, 저장 항목의 누락을 대조한다.
- 이 문서는 소스 탐색에서 확인한 기능의 명세 초안이다. 구현된 모든 분기·환경을 완전히 보장하는 커버리지 증명은 아니다.
- 기존 pytest/JavaScript 테스트는 이 사용자 시나리오와 연결하되 실제 UI 조작을 대신 수행한 것으로 집계하지 않는다.
- 자동화 구현 시 먼저 테스트 데이터 준비/초기화와 P0 사례를 연결하고, 이후 P1/P2를 추가한다. 전체 기능 검증 목표에서 P1/P2를 제외하지 않는다.
- 이 명세 작성 당시 모든 사례는 NOT_RUN이었다. 이후 브라우저 자동화의 실행 결과와 미연결 사례는 `test_results/browser/last-run.json`이 가리키는 `coverage.md`에서 확인한다. 문서 구조 검증과 앱 동작 검증은 별도로 관리한다.
